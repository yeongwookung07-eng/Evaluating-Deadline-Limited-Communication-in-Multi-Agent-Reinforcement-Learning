# SMACv2 delivery-attribution transfer (registered 2026-11-21)

Purpose: test whether the existing deadline communication evaluation controls can be applied on a learned standard MARL task, not show that DAC must win. User explicitly requested training, evaluation, verification and a narrowly scoped KBS addition. This isolated follow-up does not change the historical charter, framework, external, Hallway results, native SMACv2 or prior checkpoints.

Question/contract: with a frozen learned policy, same reset, lambda=1, shared link and cutoff, can lower offered traffic preserve the full timely delivery/cache/action history? Separately, how do Ideal Full/No-Comm/Full/RR/DAC affect held-out return, wins, goodput and CPU cost? Full and RR identity is tested on the same environment stream with independent hidden/cache/scheduler states. Both proposed actions must agree at every step for a full-trajectory identity claim. No simulator snapshot or unexecuted counterfactual-return claim is made. A live SC2 process cannot be deep-copied as a Hallway Python state can.

Strongest controls: Ideal Full, zero-message deployment, matched-cache RR, fixed-readiness primary versus measured-readiness sensitivity; all five deployments use the same checkpoint. Shadow Full/RR comparison logs sender sets, timestamps, cached message values, hidden states, actions and byte counts. Natural episode termination and native available-action masks are retained. Dead-agent participation follows the retained harness and is disclosed. Standard endpoints are zero-shot deployments of Ideal-trained weights, not independently trained algorithms or a task-necessity proof.

Competing explanations: learning failure, native simulator nonrepeatability, zero-shot distribution shift, early cache filling, lambda differences, measured CPU jitter and low power (3 training seeds). No claim of native QMIX, native VBC/TMC/SchedNet reproduction, or universal scheduler advantage. SMAC game time is not mapped to real control milliseconds; the link/deadline is an imposed evaluation model.

Registered learning budget: Terran 5-vs-5 procedural SMACv2 only, same architecture/settings as prior pilot, continue each of all 3 seed checkpoints (~100k steps) at common total-step milestones 300k, 600k, 1M, stop after the first common milestone with all three gate wins >=20% and positive mean improvement over the original untrained 0% reference. 64 gate episodes (52000000+index) and 16 fresh held-out endpoints (53000000+index), separate from training and old pilot resets. Checkpoint selection uses gate data only and is disclosed. No seed dropping. At most ~2.7M additional environment steps, at most 12h campaign. GPU0/1 optimization; GPU2 excluded. No existing jobs interrupted.

Continuation retains online/target/optimizer/update counters; replay and environment restart because pilot did not persist replay/RNG state. Exploration is reset once to .30 and annealed to .05 over 200k new steps, not an exact resume; parameters, target interval, loss and network unchanged. Phase transitions retain checkpoint counters but refill replay. This is a bounded learning feasibility extension, not arbitrary tuning until success.

Evaluation: slow20kB/s/5ms and medium100kB/s/2ms, all methods lambda1 to isolate selection, 120B step credit cap where applicable, 48B wire/32B payload, Rpost450us. Primary fixed-readiness500us still measures actual CPU separately; measured sensitivity cannot certify hard wall-clock delivery. Each held-out episode starts a fresh engine with the same engine/reset seed across methods to avoid hidden SC2 RNG carryover. No-op independent-engine repeats test reproducibility before inferential results. Warmup2 episodes, GC off within episodes, one CPU thread, evaluation jobs serial to avoid evaluation worker contention.

Falsification/adoption: any full-history mismatch rejects identity for that episode; retained mismatches are reported, not filtered. Gate failure blocks scheduler interpretation. Ideal-NoComm and DAC-RR report seed-paired differences, bootstrap CIs and raw seed/episode rows without assuming positive effects. Successful transfer means controls execute with valid identity/replay checks and expose interpretable mechanisms; it does not require DAC to win. Scientific superiority requires separate evidence.

## Terran sender substitution, 2026-11-28 (registered before runs)

Question: Does changing one admitted/delivered sender at step 8, from a common RR prefix and frozen policy, change actual subsequent return in standard Terran 5v5 SMACv2? Does it change the immediate joint action? Use all three previously gated 300k Ideal-trained checkpoints, not independent retraining. Code: `terran_sender_branch_replay.py`. Config: `../configs/terran_sender_branch_replay.yaml`. Output: `../runs/terran_sender_branch_replay_20261128_001`. CPU only (one PyTorch thread); serial, 25 minute cap. Config registered before technical probe or any endpoint.

Use 10 fresh resets per checkpoint, shared across seeds, fixed Slow/5 ms, readiness 500 µs, cache decay 1. RR serves one sender in rotating order. On the first eight actual decisions run RR. At step 8 enumerate all five single-sender slots (retain inactive IDs exactly as in the earlier harness), charge each intervention 48 offered bytes, require one timely 32 B payload. Thereafter resume RR with its factual cursor/credit. The immediate endpoint compares computed joint actions on identical input, across all five forced alternatives, with the natural RR action as no-op. A trajectory ending before the branch contributes zero to episode-weighted contrasts. Report seed-level proportions/means, all ten resets equally weighted, per-seed differences and descriptive seed-t interval for factual minus uniform realized suffix return only when the gate passes.

Historical diagnosis: rerun the failed historical seed-1 reset in fresh engines three times; log pre/post-observations, native unit records, available actions, reward, termination and learned-policy state to identify the first exact mismatch. The original stored digest has no field breakdown. Recovery test: native SC2 QuickSave/QuickLoad plus independent Python wrapper/RNG and policy state snapshots at the branch. Compare a complete factual suffix with the forced-original restored suffix step by step including all native unit records, available actions, local obs, global state, actions, cache/hidden, rewards and successor state/termination. If QuickSave is unavailable, independently reset and replay the entire identical eight-action prefix including successor checks, with analogous full factual-repeat control. No filtering mismatching cases or post hoc tolerances. Any loss of common prefix/no-op agreement suppresses pooled causal suffix-return inference for all seeds; always retain a physically common decision input to evaluate immediate action sensitivity across all three checkpoints. Neither winning a gate nor action sensitivities alone imply improved score or a general scheduler advantage. No native method comparison, CPU speed or deadline enforcement estimate. Raw step digests plus numeric first-divergence diagnostics, interventions and returns retained. Technical API probe uses separate reset outside evaluation. All failed attempts preserved.

Diagnostic implementation detail before outcome: legacy vs locally RNG-scoped get_obs adapters are each run at historical reset 52999901 with outer Python/NumPy seeds 197,198,199 to expose ambient dependence. API probe alone confirmed quick_save and quick_load requests are accepted. Save/load availability for attribution requires observable-state and complete forced-original suffix validation. If that validation fails, the separately retained confirmed action endpoint is computed on the common decision, and fresh-engine deterministic prefix/forced-factual recovery can be tested with the same prospective no-op gate.
